# Federated Operational Identity
## Delegation, Context Transfer, Shared Effects & Cross-Agent Accountability

**Control task:** `task:harness-campaign6-federated-operational-identity-20260819`  
**Standing:** programme-level investigation. HaF0–HaF61 remain frozen; HaF62 remains UNKNOWN / NOT SELECTED / NOT ADMITTED.

## 1. Research question

When multiple independently bounded Agent-facing operational subjects participate in related work, what local identities and cross-subject relations must Harness preserve so that delegation, Context/evidence transfer, shared external realization, branching and accountability remain explicit without inventing one global Run, one global Context or one group mind?

## 2. Terminology guard

`Federated Operational Identity` is a campaign label, not a commitment that identity alone is the semantic core.

Round 1 may revise the core toward **Federated Operational Relations (FOR)** if delegation/adoption/effect/accountability relations prove more fundamental than one federation identity object.

## 3. Local operational subject

A bounded `AgentOperationalSubject S_i` is the subject-relative operational locus to which Harness binds local Run/Context/proposal/adoption relations for the investigation.

It is **not** assumed identical to:

- OS process;
- model/provider instance;
- network connection/channel;
- human identity;
- Host Task;
- one immutable long-lived persona.

Subject identity must be established by the relevant operational contract/lineage, not inferred from infrastructure coincidence.

## 4. Prebound local/federated relation stack

### F0 — Local Subject & Run

Each subject `S_i` has local Run/continuation semantics from Campaign 1. Related Agents do not automatically share one RunEpisode.

### F1 — Shared Work / Host Relation

Multiple local Runs may relate to one durable Host Task or external goal. Shared work identity is not local Run identity.

### F2 — Delegation Contract

A directional delegation `D_{i→j}` states what operational authority/capability/claim-making role is delegated, scope, constraints, lineage, currentness and revocation semantics.

Delegation is not assumed to copy all authority or truth ownership.

### F3 — Delivery vs Adoption

Message/Context/evidence delivery to `S_j` is distinct from admission/adoption into `S_j`'s Effective Decision Context or OCSS.

### F4 — Local Context

Each subject retains its own Effective Decision Context and sufficiency obligations. Shared source artifacts do not imply identical cognition or Context.

### F5 — Shared Realization Claim, Local Evidence Standing

Subjects may refer to the same externally scoped Realization Claim `Q`, while each has distinct admissible evidence standing for Q until evidence is adopted/reconciled.

### F6 — Invocation / Duplicate Effect Relation

Multiple local subjects may issue distinct Invocations that target the same external capability/claim, creating duplicate/conflicting realization risk. Logical federation does not collapse Invocation cardinality.

### F7 — Cross-Subject Accountability / OCSS

OCSS support/evidence can be transferred or cited across subjects only through explicit provenance/adoption/binding. One subject's support standing is not automatically another's cognition or adequate accountability.

### F8 — Branch / Partition Continuation

A shared predecessor may produce multiple local successor branches. Branch ancestry does not make branches one Run or establish convergence.

### F9 — Reconciliation

Later reconciliation may relate branches, evidence and claims while preserving prior local history. Reconciliation does not rewrite divergent local pasts into one fabricated history.

### F10 — Local Completion / Shared Completion

One local CompletionProposal establishes only its bounded proposal role. Shared/Host/domain completion requires the authority that owns that completion relation.

## 5. Proposition P6 — Local Subjects + Typed Federation Relations

A technology-neutral Harness federation criterion can remain owner-preserving if federation is modeled as local operational subjects connected by typed delegation/adoption/effect/accountability/branch relations rather than one global operational identity/state.

### P6-A — Shared work != shared Run
### P6-B — Subject identity != process/channel/model identity
### P6-C — Delegation is directional, scoped and currentness-sensitive
### P6-D — Delegation != authority copy != truth-owner transfer
### P6-E — Delivery != adoption != cognition
### P6-F — Shared artifact != shared Effective Context
### P6-G — Shared Q != shared evidence standing
### P6-H — Shared receipt visibility != shared knowledge

### P6-J — One subject's completion proposal != federation/Host completion

### P6-L — Branch ancestry != federation convergence

## 6. Rival models

### R1 — One Global Run
All participating Agents are represented as one RunEpisode.

### R2 — One Global Context
All delivered/shared information is treated as one shared cognition/Context.

### R3 — Process/Channel Equals Agent Identity
Agent subject identity is inferred from process, session, socket or provider instance.

### R4 — Delegation Copies Full Authority
Any delegation transfers the caller's entire authority envelope.

### R5 — Delegation Transfers Truth Ownership
Delegating action/observation transfers domain/Runtime/Network/Normative truth authority.

### R6 — Delivery Equals Adoption
A message/evidence item reaching an Agent is treated as admitted cognition/support.

### R7 — Shared Receipt Equals Shared Effect Knowledge
Receipt visibility to one node is treated as global federation knowledge.

### R8 — Shared Q Has One Global Evidence State
All subjects must have the same standing for a shared Realization Claim.

### R9 — Federation Deduplicates Invocations
Related Agents invoking the same target are assumed to create one external realization.

### R10 — One Agent Completion Completes Group
One local CompletionProposal closes the shared task/federation.

### R11 — Evidence Citation Equals OCSS Adoption
Cross-Agent reference is enough to transfer support/accountability standing.

### R12 — Split Branches Are Still One Run
Partitioned/successor branches remain one operational identity merely due ancestry.

### R13 — Reconciliation Rewrites History
Later agreement replaces divergent branch histories.

### R14 — Revocation Erases Prior Delegated Effects
Withdrawing delegation retroactively removes prior effect/provenance standing.

## 7. Falsifier classes

P6 must be revised/rejected if:

1. local Run identity cannot coexist with shared work;
2. delegation cannot be represented without full authority transfer;
3. delivery necessarily equals adoption/cognition;
4. shared Q cannot carry subject-relative evidence standing;
5. duplicate Invocations cannot be represented independently;
6. cross-Agent OCSS cannot preserve provenance/adoption boundaries;
7. branch continuation requires one global Run state;
8. reconciliation requires history rewrite;
9. delegation revocation necessarily erases prior effect standing;
10. the criterion requires Network consensus/path semantics owned outside Harness;
11. operational attribution necessarily becomes normative blame/team responsibility;
12. the criterion requires a concrete multi-agent framework/process model.

## 9. Expected tendencies

- T1: one Host Task may relate multiple local Runs.
- T2/T3/T24: subject identity is not infrastructure identity.
- T4–T8: delegation is scoped/current; revocation changes future authority, not prior history/effects.
- T9–T11: delivery and shared artifacts do not create shared Context.
- T12/T15: same Q may have different local evidence standing.
- T13: adoption can transfer admissible evidence without transferring truth ownership.
- T14: federation does not deduplicate Invocation/effect cardinality.
- T16: local proposal does not close peers/Host Task.
- T17/T18: OCSS adoption/dependency semantics remain explicit.
- T19/T20: branch identity/history survives reconciliation.
- T22: delivery truth and remote cognition/adoption remain distinct.
- T23: OPUR evaluates preservation obligations across moved/split cuts.

## 10. Evidence classes

Campaign 6 distinguishes:

- `DIRECT_FEDERATION_ENGINEERING_EVIDENCE` — true multiple AgentOperationalSubjects interacting;
- `ADJACENT_ENGINEERING_EVIDENCE` — delegation/adoption/caller ingress/cross-process mechanisms that pressure one relation but do not instantiate federation;
- `CONCEPTUAL_ONLY` — destructive cases without current engineering fixture.

Current pre-analysis expectation: adjacent evidence only.
