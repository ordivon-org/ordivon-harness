# AM2 — Loop Boundary Falsifiers

Status: active research contraction.

## Result 1 — identity is cheaper than substitutability

AM1 established that a Loop implementation can be named in an immutable Attempt without changing Run authority: `HarnessExecutionProfile.metadata.loopDriver` is strict, participates in Profile digest, and is copied into the exact system manifest.

The first executable factory seam did **not** survive AM2 review. Two independent falsifiers defeat it before a second driver is even promoted:

1. **implementation-byte falsifier** — a caller-supplied `driverDigest` was only a declared identity. Nothing mechanically proved that the Python callable/factory being executed had those bytes or that the digest named its transitive implementation.
2. **behavioral-kernel falsifier** — requiring `isinstance(loop, OrdivonAgentLoop)` does not prove that a subclass/override preserves ProviderCallLifecycle, Turn projection/admission, Tool intent/fence/receipt, budget accounting, UNKNOWN or recovery. Python type ancestry is not an execution-semantics proof.

Therefore AM2 contracts the seam to `HarnessLoopDriverIdentity`: it is addressability/evidence only. `StandaloneHarnessRunner` regains its original construction path and exposes no arbitrary Loop factory.

This is a positive result: **Loop identity may be morphology; Loop substitutability has not yet been earned.**

## Result 2 — required non-bypassable kernels

A future executable LoopDriver boundary must make the following current responsibilities non-bypassable rather than merely documenting them:

- exact `AgentTurnRequest` construction and request-bound capability truth;
- durable Provider claim/dispatch/completion/UNKNOWN lifecycle;
- exact Tool surface/grant and per-effect intent/fence/receipt/reconciliation;
- Run/Attempt budgets, deadlines, cancellation and no-progress/effect gates;
- WorkingSet/caller-ingress provenance and cognition admission;
- trace/receipt evidence sufficient for fresh-process recovery;
- caller/domain completion remaining outside the loop.

A driver may vary scheduling/control-flow **around** these kernels only after the kernels can be composed without handing the driver a bypass path.

## Result 3 — Deliberation is evidence for topology variation, not yet a LoopDriver

Current `DeliberationThenToolRunner` proves a materially different two-phase cognition topology already exists:

```text
no-Tool deliberation
→ non-authoritative cognition record
→ same-Context Tool phase
```

Its source explicitly preserves `deliberation != world truth`, `deliberation != Tool intent`, and caller-supplied Tool authority. The lifecycle-bound form also accounts aggregate budget/deadline/cancellation across phases.

However, it is not implemented through the current durable `StandaloneHarnessRunner` Provider-call continuity path and therefore cannot simply be relabeled as a replacement LoopDriver. Doing so would collapse two separately evidenced products into a type abstraction.

AM2 therefore uses it as a **control-flow challenger**: it proves different loop topology is useful/real, while simultaneously proving the current extraction boundary is not yet sufficient for safe substitution.

## Multi-Agent / Entity threshold falsifiers

The AM0 threshold survives the first code-level attack:

### Internal cognition helper

A critic/planner/verifier invoked only inside one parent Run, with no independently durable identity, Tool grant, World trajectory or destination Presence, remains Harness morphology. Its result is cognition/evidence requiring parent admission.

### Persistent actor

If a child needs its own durable cognition continuity plus independently addressable external consequence authority or Resource/Message/Entity trajectories, treating it as a hidden loop implementation would erase owner-native identity and recovery. It must cross into World/domain Entity semantics.

The deletion falsifier is exact: if removing the child's independent identity would make two external consequences, receipts, migrations or authorities alias, it is not merely an internal sub-agent.

## Consequence-bound replacement classes

AM2 derives two replacement classes from World/Runtime/Host current laws:

### Pre-consequence morphology replacement

Before any exact owner consequence is prepared/admitted, planning state is recomputable. Model/loop/context strategy may be replaced by a new Attempt after current owner reality is re-observed.

### Post-consequence morphology replacement

After an exact consequence identity is prepared/dispatched/bound, the replacement cannot reinterpret or discard it. A fresh morphology must first inherit/reconcile the original owner identity and any Receipt/UNKNOWN state. An exact `not_committed` proof may reopen the original retry path where the owner contract supports it; absence of a receipt is not such proof.

## Minimum Relational Quiescence candidate

A full morphology transition is *relationally quiescent* only when all consequence owners relevant to the transition can establish one of:

- no admitted outstanding consequence exists; or
- every admitted consequence is terminal with exact retained receipt; or
- an owner-native exact `not_committed` proof explicitly makes the original retry safe.

`UNKNOWN` is therefore **not quiescent**.

This is a derived cross-owner predicate, not a new database or global transaction. AM3 must test it using real World trajectory and Harness/Runtime evidence before AM4 can consider an executable quiescence gate.

## AM2 decision

Retain:
- Attempt-bound LoopDriver **identity**;
- Loop/topology as a candidate morphology coordinate;
- the requirement to extract non-bypassable kernels before executable substitution;
- the internal-helper vs persistent-Entity threshold;
- the Relational Quiescence candidate.

Delete/contract:
- arbitrary Loop factory execution from `StandaloneHarnessRunner`;
- type-ancestry as proof of Loop semantic compatibility.

Do not add:
- global registry;
- live HMR;
- universal Agent topology state;
- synthetic cross-owner transaction manager.

Next: AM3 should physically test World relation continuity across morphology/process replacement, especially `Receipt`, `UNKNOWN`, and `not_committed` trajectories.
